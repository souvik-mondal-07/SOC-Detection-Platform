# Detection Rule Management (Step 7)

Detection rules are data stored in MongoDB and managed through a REST API. The detection engine (Step 6) is unchanged: it consumes whatever enabled rules are stored. This step adds validation, a service layer and the management API around them. Authentication, alerts and a rule-management UI are later steps.

## Architecture

```text
Rule Management API (/api/v1/rules)        Detection API (/api/v1/detection)
        │                                             │
        ▼                                             ▼
   RuleService                                 DetectionService
        │                                             │
        └────────────► DetectionRuleRepository ◄──────┘
                              │
                              ▼
                MongoDB  detection_rules  (single source of truth)
                              │
                     enabled rules, read on every evaluation
                              ▼
                  DetectionEngine / RuleEvaluator
```

- `app/api/v1/rules.py` translates HTTP to service calls and errors to the response envelope. No MongoDB queries.
- `app/services/rule_service.py` validates, enforces business rules and talks to the repository. No HTTP code. The detection engine does not import it.
- `app/repositories/detection_rule_repository.py` owns every query (filtering, counting, paging, delete).
- Rules are not duplicated anywhere in `engine.py`, `rule_evaluator.py` or `detection_service.py`. The detection service loads enabled rules from the repository for each request, so there is no cache to invalidate.

## Rule structure

```json
{
  "rule_id": "AUTH-001",
  "name": "Multiple Failed Logins",
  "category": "authentication",
  "description": "Detect repeated failed authentication attempts",
  "severity": "high",
  "enabled": true,
  "conditions": {
    "event_type": "authentication",
    "status": "failed",
    "threshold": 5,
    "window_minutes": 5,
    "correlation_field": "source_ip"
  },
  "created_at": "2026-10-02T10:00:00Z",
  "updated_at": "2026-10-02T10:00:00Z"
}
```

The stored document structure is the same as in Step 3.

| Field | Rule |
| --- | --- |
| `rule_id` | Required, unique, immutable. Format `PREFIX-NNN`: 2 to 10 capital letters, a hyphen, 3 or more digits (`AUTH-001`, `PRIV-012`) |
| `name` | Required, 1 to 120 characters |
| `description` | Required, 1 to 1000 characters |
| `category` | One of the supported categories |
| `severity` | `low`, `medium`, `high` or `critical`. Anything else (`urgent`, `danger`, `severe`) is rejected |
| `enabled` | Boolean only (`"yes"`, `1` and `"true"` are rejected). Defaults to `true` on create |
| `conditions` | Object, see below |
| `created_at`, `updated_at` | Generated by the server. Requests that contain them are rejected, so clients cannot set them |

### Supported categories

`authentication`, `web`, `network`, `privilege`, `system`, `application`, `correlation`. Custom categories are not supported; add a value to `RuleCategory` in `app/models/rule.py` to introduce one.

## Conditions

Conditions are validated with the engine's own parser (`app/detection/conditions.py`), so a rule that can be saved is a rule the engine can interpret. Unknown keys are rejected. Conditions are data only: nothing is ever evaluated as code, and no expressions are accepted.

| Field | Meaning |
| --- | --- |
| `event_type` | `authentication`, `web`, `network`, `privilege`, `system` or `application` (exact match) |
| `status` | `success`, `failed`, `blocked` or `unknown` (exact match) |
| `action`, `source` | Lowercase snake_case, exact match (for example `login`, `linux_auth`) |
| `username_present`, `source_ip_present` | `true` requires the event to carry that field |
| `metadata` | `{key: value}` or `{key: [values]}` exact or any-of match on event metadata (max 10 keys, 20 values each) |
| `threshold` | Number of matching events (or distinct values) needed. Integer, 1 to 1000 |
| `window_minutes` | Time window. Integer, 1 to 1440 (24 hours). Required with `threshold` or `preceded_by` |
| `distinct_field` | Count distinct values of `username`, `source_ip` or `metadata.<key>` instead of events. Requires `threshold` |
| `correlation_field` | Group by `source_ip` (default) or `username`. Only for threshold, distinct and sequence rules |
| `preceded_by` | Sequence rule: `{<filters>, "min_count": N}` events that must occur before the triggering event within `window_minutes` |

Rules of combination: at least one filter is required (otherwise the rule would match every event); `threshold` needs `window_minutes` and vice versa; `preceded_by` cannot be combined with `threshold`.

The maximum threshold is 1000 rather than 100000: the evaluator reads at most 5000 events per evaluation, so larger thresholds could not be evaluated reliably. The window limit of 1440 minutes bounds query cost.

Exact-match `username` and `source_ip` filters are not part of the engine's vocabulary. Rules describe behavior (counted per `correlation_field`), not named actors, so they are rejected as unknown condition fields.

## Lifecycle

```text
create ──► enabled ◄──► disabled ──► delete
              │
              └─ update (name, description, category, severity, enabled, conditions)
```

- Create: validated, `created_at` and `updated_at` set by the server.
- Update: partial. Send only the fields to change; the merged rule is re-validated before it is saved, so an invalid update never alters the stored rule. `rule_id` and `created_at` cannot change. `updated_at` is refreshed.
- Enable or disable: a dedicated endpoint. A disabled rule is not loaded by the detection service and cannot match.
- Delete: removes the document. The five initial rules (`AUTH-001`, `AUTH-002`, `AUTH-003`, `WEB-001`, `NET-001`) are protected from accidental deletion: the API returns `409 RULE_PROTECTED` unless `?force=true` is given. Disabling is the normal way to turn one off. This is an accident guard, not authorization.

## API

Base path `/api/v1/rules`.

| Method and path | Success | Errors |
| --- | --- | --- |
| `GET /rules` | `200` summary list | `422` invalid filter or paging value |
| `GET /rules/{rule_id}` | `200` full rule | `404 RULE_NOT_FOUND` |
| `POST /rules` | `201` full rule | `409 RULE_ALREADY_EXISTS`, `422` validation |
| `PUT /rules/{rule_id}` | `200` full rule | `404`, `422` validation |
| `PATCH /rules/{rule_id}/status` | `200` `{success, rule_id, enabled}` | `404`, `422 INVALID_STATUS` |
| `DELETE /rules/{rule_id}` | `200` `{success, rule_id, message}` | `404`, `409 RULE_PROTECTED` |

### Listing, filters and pagination

Filters: `category`, `severity`, `enabled`, and `name` (case-insensitive substring). They combine with AND and are applied in the MongoDB query, not in Python. Paging uses `page` (from 1) and `limit` (default 20, maximum 100). `total` counts all matching rules; `count` is the number in this page. Rules are ordered by `rule_id`.

```text
GET /api/v1/rules?category=authentication&enabled=true&page=1&limit=20
```

```json
{
  "success": true,
  "page": 1,
  "limit": 20,
  "total": 3,
  "count": 3,
  "rules": [
    {"rule_id": "AUTH-001", "name": "Multiple Failed Logins", "category": "authentication", "severity": "high", "enabled": true}
  ]
}
```

### Errors

Every rule endpoint returns the same envelope. Messages never include stack traces, connection strings or the submitted values.

```json
{"success": false, "message": "Detection rule already exists", "error_code": "RULE_ALREADY_EXISTS"}
```

| `error_code` | Status | When |
| --- | --- | --- |
| `RULE_NOT_FOUND` | 404 | Unknown `rule_id` |
| `RULE_ALREADY_EXISTS` | 409 | Duplicate `rule_id` on create |
| `RULE_PROTECTED` | 409 | Deleting an initial rule without `force=true` |
| `INVALID_RULE` | 422 | Missing or malformed field, unknown field, bad `rule_id`, empty update, bad paging |
| `INVALID_CONDITION` | 422 | `conditions` is not an object or fails condition validation |
| `INVALID_SEVERITY` | 422 | Severity outside the enum |
| `INVALID_CATEGORY` | 422 | Unsupported category |
| `INVALID_STATUS` | 422 | `enabled` is not a boolean |
| `DATABASE_UNAVAILABLE` | 503 | MongoDB cannot be reached |

Validation errors may include a `details` list of `{field, message}` entries.

## MongoDB storage and indexes

Collection `detection_rules`. Indexes (created idempotently at startup and by `initialize_database`; existing indexes are never recreated):

| Index | Purpose |
| --- | --- |
| `uq_rule_id` (unique) | No duplicate rule IDs, lookups by ID |
| `ix_category` | Filter by category |
| `ix_severity` | Filter by severity (added in Step 7) |
| `ix_enabled` | Engine loads enabled rules; filter by status |

## Seeding

`python ..\scripts\seed_detection_rules.py` (from `backend`) upserts the five initial rules by `rule_id`. It can be run any number of times without creating duplicates. It refreshes name, category, description, severity and conditions, but keeps an existing rule's `enabled` flag and `created_at`, so re-seeding never re-enables a rule an operator disabled. It never deletes, and recreates an initial rule that was force-deleted.

## Detection engine integration

`DetectionService` calls `DetectionRuleRepository.get_enabled_rules()` for each evaluation request. Consequences, all covered by tests:

- Disable `AUTH-001` and the same event no longer matches it; enable it again and it matches again.
- Updating `threshold` changes the next evaluation.
- A newly created rule is evaluated immediately; a deleted rule no longer is.
- A stored rule whose conditions the engine cannot interpret is skipped and reported in `skipped_rule_ids`; it never stops the other rules.

## Security

- No `eval`, `exec` or expression language; conditions are validated data.
- Request bodies are validated by Pydantic schemas that reject unknown fields, including client timestamps.
- Condition keys beginning with `$` or containing `.` are rejected, and `name` search text is escaped before it reaches MongoDB.
- Errors are generic and never echo submitted values or internals.

## Limitations

- No authentication or authorization: anyone who can reach the API can change rules. Run locally with authorized data only until a later step adds access control.
- `PUT` is a partial update (only the supplied fields change), not a full replacement.
- Rule changes are not versioned or audited.
- The delete guard is a convention (a fixed list of initial rule IDs), not a permission check.
