# Alert Investigation Workflow (Step 11)

A SOC analyst can open an **investigation** for one or more alerts, link and unlink alerts, record findings as notes over time, and move the investigation through a simple status lifecycle.

> **No authentication yet.** The investigation API is for the **local development environment only**. Anyone who can reach the backend can read and change investigations. JWT authentication and role-based access are outside this step.

## Design rules

- Investigation status is **separate** from alert status. Nothing here changes an alert's status, severity or priority, and linking never marks an alert resolved or false positive.
- An investigation stores **alert IDs only**. Alert details are read live from the `alerts` collection, so alerts remain the single source of truth.
- Layers: routes (`api/v1/investigations.py`) → service (`services/investigation_service.py`, all business rules) → repositories (all MongoDB access).
- No automated response, notifications or AI summaries.

## Investigation lifecycle

Statuses: `open` (default), `in_progress`, `closed`.

> The Step 11 brief names the final state `completed`. Step 3 already stored `closed`, so `closed` was kept for compatibility. Renaming it is a one-line change in `models/investigation.py` (`InvestigationStatus`) and `types/investigations.ts`.

| From \ To | open | in_progress | closed |
| --- | --- | --- | --- |
| open | – | yes | yes |
| in_progress | yes | – | yes |
| closed | **no** | yes (reopen) | – |

Setting the current status again is accepted and changes nothing (`updated_at` stays). Any other change returns **409**. Unknown values return **422**.

## API

Base path `/api/v1/investigations`. Errors use `{"error": {"message": "..."}}` (validation errors add `details` with field and message, never the submitted value).

| Method and path | Purpose | Success |
| --- | --- | --- |
| `GET /investigations` | List, newest first. Query: `status`, `alert_id`, `title` (substring, case-insensitive), `page` (default 1), `limit` (1–100, default 20) | 200 |
| `POST /investigations` | Create from existing alerts | 201 |
| `GET /investigations/{id}` | Detail with live alert context and notes | 200 |
| `PATCH /investigations/{id}` | Change `title` and/or `status` | 200 |
| `POST /investigations/{id}/alerts` | Link one or more existing alerts | 200 |
| `DELETE /investigations/{id}/alerts/{alert_id}` | Remove the link only | 200 |
| `POST /investigations/{id}/notes` | Append a note | 201 |

Create:

```json
POST /api/v1/investigations
{ "title": "Brute force from 10.0.0.9", "alert_ids": ["ALT-20261014-000001"] }
```

Response (the same detail shape is returned by every write):

```json
{
  "success": true,
  "investigation": {
    "investigation_id": "INV-20261014-000001",
    "title": "Brute force from 10.0.0.9",
    "status": "open",
    "alert_count": 1, "note_count": 0, "unavailable_alert_count": 0,
    "created_at": "2026-10-14T15:00:00Z", "updated_at": "2026-10-14T15:00:00Z",
    "alert_ids": ["ALT-20261014-000001"],
    "alerts": [{
      "alert_id": "ALT-20261014-000001", "available": true, "rule_id": "AUTH-001",
      "title": "Multiple Failed Logins Detected", "severity": "critical", "priority_score": 95,
      "status": "open", "source_ip": "10.0.0.9", "created_at": "2026-10-14T14:58:00Z",
      "event_count": 5, "event_ids": ["evt_00001", "evt_00002"]
    }],
    "notes": []
  }
}
```

Other requests: `PATCH {"status": "in_progress"}` or `{"title": "New title"}`; `POST .../alerts {"alert_ids": ["ALT-..."]}`; `POST .../notes {"text": "Source IP is on the allow-list."}`.

List response: `{"success": true, "page", "limit", "total", "count", "investigations": [{investigation_id, title, status, alert_count, note_count, created_at, updated_at}]}`.

### Errors

| Situation | Status |
| --- | --- |
| Malformed ID, empty/oversized/unknown field, bad status value, empty or duplicate `alert_ids`, more than 100 IDs per request | 422 |
| Investigation not found; alert in the request does not exist (nothing is created or linked); unlinking an alert that is not linked | 404 |
| Alert already linked; invalid status transition; unlinking the last alert; note or alert count limit reached | 409 |
| MongoDB unreachable | 503 `Database is unavailable` |
| Anything unexpected | 500 `Internal server error` (no details) |

## MongoDB structure

Collection `investigations` (model `models/investigation.py`):

| Field | Notes |
| --- | --- |
| `investigation_id` | `INV-YYYYMMDD-NNNNNN`, generated by the server, unique |
| `title` | 1–200 characters |
| `status` | `open` `in_progress` `closed` |
| `alert_ids` | 1–1000 unique alert IDs |
| `notes` | list of `{note_id, text, created_at}`, up to 500 |
| `created_at`, `updated_at` | UTC; `updated_at` changes on every real change |

Indexes: `uq_investigation_id` (unique), `ix_status_created_at`, `ix_created_at`, and **new** `ix_alert_ids` (multikey, for "investigations containing this alert"). They are created automatically at startup and by `python -m app.repositories.initialization`. No migration is needed: the only schema changes are the optional `note_id` (generated when missing) and the new index.

## Alert linking

- Every alert ID is checked against `alerts`; any unknown ID rejects the whole request (alerts are never created here).
- Already-linked IDs are rejected (409) and nothing is linked. Writes use MongoDB `$addToSet`/`$pull`, so a duplicate can never be stored even under concurrent requests.
- The same alert may be in several investigations.
- An investigation must keep **at least one** alert (the Step 3 model requires it), so the last alert cannot be unlinked.
- Unlinking removes the link only; the alert is untouched.
- If an alert was deleted from the database (no API deletes alerts today), it appears with `available: false` and only its ID, and can be unlinked.
- Per alert, at most 50 `event_ids` are returned; `event_count` has the full number.

## Notes

Notes are append-only entries with a generated `note_id`, text and timestamp, shown oldest first. Text is trimmed, must be 1–2000 characters, and is stored and rendered as plain text. There is **no author field** because there is no authentication; the system does not claim who wrote a note.

## Security limitations before authentication

- No login, roles or audit attribution: any local client can read and modify investigations and notes.
- CORS only limits browsers, not other clients. Do not expose this backend beyond the development machine.
- Clients cannot send MongoDB query objects: IDs and statuses are validated, the title search is an escaped literal, and unknown JSON fields are rejected.

## Run and test (PowerShell, from the project root)

```powershell
# Backend (MongoDB must be running)
cd backend
.\.venv\Scripts\Activate.ps1
uvicorn app.main:app --reload --port 8000

# Frontend, in a second terminal
cd frontend
npm run dev
```

Open http://localhost:5173/investigations. Generate alerts first (see the README) so there is something to link.

```powershell
cd backend; python -m pytest tests/investigations      # investigation tests
cd backend; python -m pytest                            # whole backend suite
cd frontend; npm test; npm run build
```
